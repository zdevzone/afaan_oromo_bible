# Release strategy

Status: approved release process for Windows, macOS and Linux; edition distribution rights, signing accounts/keys, supported OS floors and architecture artifacts require verification. The first public production release is **V1.0**, regardless of the number or labels of development iterations. Linux is a required V1 target; its full native development build and bounded offline X11 smoke pass, while the release qualification below and Windows/macOS native evidence remain pending.

## Release stages

| Stage                  | Purpose                                                | Exit evidence                                                                                                            |
| ---------------------- | ------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------ |
| Phase 1 development    | Prove one React/native slice and tooling               | Browser checks plus real Tauri SQLite read/write/restart evidence; missing native prerequisites remain explicit blockers |
| Phase 2 internal alpha | Complete V1 features and authorized corpus integration | Scope acceptance checks, reproducible content pack, full data/backup journeys                                            |
| Phase 3 private beta   | Stabilize actual installed applications                | Native platform testing, Oromo review, accessibility review and recovery drills                                          |
| Phase 4 public V1.0    | Publish trusted desktop packages                       | All gates below, platform-appropriate signatures/verification and release notes                                          |

Private testers must receive an explicit development-data notice before use: schemas and backups can be reset or replaced until V1.0, and experimental records are not promised preservation. Keep private distribution within verified content permissions; private testing does not waive licensing. Do not call a build public production while using the pre-release data policy.

## Platform and packaging decisions

The initial package choices are a signed Windows NSIS installer, macOS `.app` distributed in a `.dmg`, and Linux `.deb`. Each needs a verified install/uninstall test. MSI is optional for a demonstrated Windows deployment need. An AppImage is optional only after separate qualification; do not promise it, additional Linux distributions/architectures, package managers or stores merely because the bundler supports an output format.

Validate package dependency resolution on a clean Ubuntu installation without developer tools. Include a desktop launcher and usable application icon, and verify launch from GNOME as well as a terminal. Additional distro releases or architectures need their own dependency/ABI, desktop and accessibility qualification before publication.

Windows requires a WebView2 runtime. Core app use is offline after installation, but a WebView2 bootstrapper can require network during installation. Decide explicitly between a prerequisite already on the machine, an installer that downloads it, or a permitted bundled offline runtime installer. Disclose which path each artifact provides; if advertised as an offline installer, it must install on a clean supported machine without internet. Verify Microsoft redistribution terms, artifact size and [Tauri's WebView2 options](https://v2.tauri.app/distribute/windows-installer/#webview2-installation-options) before claiming that path. A Linux `.deb` also does not contain every system runtime. Disclose that requirement independently of the guarantee that reading and local features work offline after installation. Test missing-dependency diagnostics and successful installation through the documented package-manager route; do not advertise fully offline installation without a clean disconnected-install test covering those dependencies.

## Signing and trust

- Windows: verify access to an appropriate Authenticode signing identity/service, sign executables/installers as required, use trusted timestamping and verify signatures on the final downloaded artifact. Test the real clean-machine install flow; signing alone does not guarantee immediate SmartScreen reputation.
- macOS: obtain the appropriate Apple Developer identity, sign nested binaries correctly with the required runtime/entitlements, notarize, staple where applicable, and assess the final application/DMG with platform verification tools. Test a downloaded/quarantined copy through Gatekeeper on a clean user account.
- Linux: publish SHA-256 checksums and an independently verifiable signature covering the `.deb` or its checksum manifest. The initial recommendation is a detached OpenPGP signature over `SHA256SUMS`, with documented verification steps and a release-key fingerprint available through a separately trusted channel. Select and verify the release key before beta. A standalone `.deb` is not automatically authenticated by APT; an optional future APT repository needs its own signed repository metadata. Do not describe this process as Linux Authenticode or notarization, or claim the standard Tauri bundler provides those mechanisms.
- CI credentials belong in the CI secret store or signing service. Never commit private keys, certificates with passwords, tokens or account secrets. Varlock validates declared build environment requirements; values exposed to the renderer must never contain these secrets.
- Missing signing credentials block public release, while local unsigned development may continue. Do not label unsigned development bundles as production ready.

Record the platform signing identity or Linux release-key fingerprint, verification result and timestamp without disclosing secrets. Confirm packaging/signing requirements against current platform and Tauri documentation when configuring them; start with [Tauri Windows signing](https://v2.tauri.app/distribute/sign/windows/), [macOS signing/notarization](https://v2.tauri.app/distribute/sign/macos/) and [Debian packaging](https://v2.tauri.app/distribute/debian/).

After the Linux release owner has selected the release key, distribute its public key and the expected primary-key fingerprint through independently trusted channels. A downloaded public key or checksum file does not authenticate itself. Users with GnuPG can verify a downloaded `.deb` and the detached signature over `SHA256SUMS` with:

```sh
python3 tools/release/verify_linux_package.py \
  "./Afaan Oromo Bible_1.0_amd64.deb" \
  ./SHA256SUMS ./SHA256SUMS.asc ./release-public-key.asc \
  EXPECTED_FINGERPRINT_FROM_TRUSTED_CHANNEL
```

The verifier imports the supplied public key into a temporary isolated GnuPG home, requires its sole primary fingerprint to match the separately obtained expected fingerprint, verifies that the detached signature was made by that primary key (or one of its signing subkeys), and compares the exact package basename and streamed SHA-256 to exactly one entry in the signed manifest. It does not install the package. It does not establish trust in a fingerprint copied from the same download location, and it is not a replacement for a signed APT repository. No release fingerprint or key has been selected yet.

## Artifact and content provenance

Each candidate records source commit, app version, toolchain/lockfile versions, content importer version, content manifest/hash, copyright/attribution, license disposition, OS/architecture and SHA-256 hashes of final installers/packages. Linux records also identify the build/runtime distribution and session matrix. Build `library.sqlite` from approved inputs with the documented pipeline; do not manually patch the release database. Keep original licensed inputs in the location allowed by their permissions, outside a public repository when required.

Package the immutable content database and required UI/fonts/icons locally. Exclude synthetic fixtures, development adapters, credentials, raw paid component packages and unauthorized source text from public artifacts. Licensed component code incorporated in the finished app must follow the actual Shadcnblocks agreement; inspect the terms before making the source repository public. Produce third-party notices for dependencies and resources using reviewed license data.

The mutable `user.sqlite` lives in the platform's application-data directory, never inside the application installation. Installer/package replacement must not overwrite user records. Uninstall behavior must be tested and documented; do not delete personal data silently. There is no remote backend requirement or mandatory account.

## Candidate checklist

A release owner records a pass, failure or explicit blocker for each item; an unchecked required item blocks V1.0.

The release-only Tauri build runs `tools/release/verify-ui.mjs` before the approved-content check. The UI gate requires `src/locales/om.json` to contain a nonblank string for every English catalog key with the same interpolation placeholders, and `content/distribution/approved-ui.json` to have exactly `formatVersion: 1`, `locale: "om"`, a nonempty `reviewEvidenceId`, and `catalogSha256` for the exact Oromo JSON bytes. The approved UI manifest is bundled for offline release inspection. A matching hash and evidence ID are mechanical checks; the release owner must separately verify the fluent review record and audience suitability. Development builds explicitly show English fallback while the Oromo catalog is incomplete. The current empty Oromo catalog intentionally fails this gate.

Every Vite build also checks `public/` before asset copying and rejects ZIP, USX, USFM, SQLite/DB files and symlinks. Keep original structured archives in ignored `content/sources/` and approved runtime content in the release-only Tauri resource mapping; `public/` is for distributable web assets. Inspect the final package as well as the renderer output before release.

The release build checks the generated Tauri renderer with `tools/release/verify-renderer.mjs` before packaging. It rejects source/database assets, browser `indexedDB` code and distinctive exact synthetic fixture passages; CI runs the same check on a Tauri-target renderer build. This is a mechanical exclusion check, not a substitute for final installer inspection or content approval.

1. All required behavior in [MVP_SCOPE.md](MVP_SCOPE.md) passes and deferred features remain excluded. No placeholder Scripture or unreviewed translation labels are presented as real content.
2. Edition source, reproduction and distribution rights, attribution, territory/platform restrictions and allowed transformations have written dispositions in [CONTENT_LICENSING.md](CONTENT_LICENSING.md). The app exposes edition and license details offline.
3. Type checking, linting, unit/integration suites, Rust tests, content verification, browser journeys and production builds pass from the recorded commit. Native suites actually run on every published OS/architecture combination.
4. Installation succeeds under the artifact's disclosed prerequisite/network conditions. Once installed, launch, read, navigate, search, copy, annotate, restart, export and restore work with network disabled. Verify no remote fonts/assets or browser adapter fallback.
5. Fluent Oromo content/UI reviewers approve the defined samples; NVDA on Windows, VoiceOver on macOS, Orca through AT-SPI on the actual Linux app, and keyboard checks pass; measured performance meets the agreed budgets. Browser accessibility alone does not establish Linux WebKitGTK accessibility.
6. Disk-full/denied-write handling, interrupted transactions, corrupt-data handling and a restore drill preserve records. Restore with an unavailable edition retains anchors and offers a useful unavailable-content state.
7. Installed app-data paths, SQLite restart/durability, clipboard, native dialogs, permissions, focus, resizing, system theme, font/Oromo rendering, backup/restore and Unicode filesystem paths work. On Ubuntu GNOME run these checks in both X11 and Wayland sessions, record the application's display backend, and verify GNOME launcher, remove/reinstall and user-data preservation. Verify shortcuts under each OS's conventions.
8. Final downloaded Windows/macOS installers pass the applicable signing/notarization/hash checks; Linux package checksums and the manifest/package signature verify using the documented public key. WebView2 and Linux runtime dependency handling pass, including a clean disconnected install for any artifact advertised as an offline installer. No release-blocking known issue remains.
9. Publish clear installation, supported-platform, backup/restore, content attribution, version and known-issue information. User-facing text matches actual behavior.

Keep reports and final artifact hashes with the release record. Missing Linux desktop, session, AT-SPI/Orca or package evidence blocks V1 just as missing Windows/macOS evidence does. Do not claim tests passed if the environment, rights, corpus or signing identity/key were unavailable. The current Ubuntu 24.04 development container passes a full embedded native debug build plus offline synthetic read/copy/search/note/restart smoke under Xvfb/Openbox. The passing `smoke-005` run also verifies Tab/Shift+Tab order, modal focus cycling, reverse traversal, Escape dismissal and focus return. This establishes early native integration, not GNOME X11/Wayland, manual Orca, `.deb` qualification or Windows/macOS readiness. See the [Linux guide](../tools/linux/README.md) and [testing evidence](TESTING_STRATEGY.md#browser-versus-native-evidence) for the procedure and its limits.

The native window-close Save/Discard/Cancel guard now passes focused logic tests and the actual synthetic Openbox Alt+F4 run recorded in `.tooling/linux/close-002`. Cancel/Escape retain the draft and focus, Discard exits with the committed baseline intact, a real SQLite write-lock timeout keeps the window/draft open, and an unlocked Save retry commits before exit and survives a new process. Clean Alt+F4 also exits. The application-level quit guard also enters the same decision flow and coalesces repeated requests in code. External SIGTERM or crashes are outside this guard; transactional durability, disk-full behavior and recovery remain independent requirements.

## Updates, data and the V1.0 boundary

Use manually downloaded application updates for V1: signed Windows/macOS installers and a Linux package verified against the signed manifest/package. No Tauri updater plugin, background download, account or update backend is required. Users obtain releases through the selected official distribution page; show an application version and a stable release link. Verify the distribution host and its ownership before publishing. TLS and checksums complement independently verified signatures but do not replace them. Test `.deb` replacement through the documented package-manager flow without overwriting user data.

Before V1.0, change schemas, APIs and internal formats directly; recreate developer databases deliberately and remove obsolete implementations. Do not add migrations or compatibility shims for abandoned development schemas. Never reset records silently on normal launch. The first public release freezes the first supported user schema and portable backup format.

Current pre-release candidates are native user-database `PRAGMA user_version = 4` and portable JSON `formatVersion = 1`. The synthetic full-record fixture at [`tests/fixtures/v1-user-backup-candidate.json`](../tests/fixtures/v1-user-backup-candidate.json) is mechanically round-tripped by `tests/contracts/v1BackupSchema.test.ts`. It prepares a stable input for public V1 backup restore/migration tests; it does not itself freeze the public contract. At the V1.0 boundary, the release record must identify the exact database and backup versions, retain representative fixtures, and pass restore/migration and interruption tests on the supported targets.

After V1.0, preserve user records, keep content and user database upgrades separate, and require tested user-database migrations before any public schema change. Take a recoverable snapshot before migration, run changes transactionally, detect unsupported newer schemas and stop without mutation on failure. Test interruption, insufficient disk space and recovery. Database downgrade is not assumed safe; document rollback via the retained compatible application/data snapshot rather than opening a newer database with older code. Support backup versions according to a published policy.

Content-pack replacement must preserve edition/versification identity rules and user anchors, and obey the source license. A text revision or removed edition needs reviewed handling before distribution. V1 does not need an independent content updater; ship validated content with the authenticated application releases above.

Personal backup is versioned JSON containing user records and edition-aware references, without Scripture payload. It is a user-controlled recovery mechanism, separate from automatic application installation. Restoration validates before mutation, requires explicit destructive replacement confirmation and a recoverable pre-restore snapshot, then replaces records atomically; V1 does not merge. Explain clearly that JSON exports contain private notes in plaintext and let the user choose the destination.

## Post-release response

Provide one documented issue/support route before release. Request version, OS and reproducible steps; for Linux also request distribution/version, package architecture and X11/Wayland session. Do not request private notes or a complete backup by default. If a serious data-loss, content-integrity or licensing issue appears, pause distribution of the affected artifact, retain its identity, communicate the affected versions and provide a tested corrective release with the applicable signature/manifest. Avoid changing released files in place under the same version/hash.

Optional automatic updates, synchronization, hosted AI and additional platforms require later scoped decisions. They must not become requirements for offline reading or delay a useful, correctly licensed V1.
